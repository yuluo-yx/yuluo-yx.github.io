# Vibe Coding 一总结

当前模型越来越多，模型能力大致追平。在使用同一个模型的前提下，大家写出来的代码应该是逐渐趋于一致的，但是现状并不是这样。而是层次不齐。

主要一个点是“**得靠谱**”。不同于之前古法时代编程：上个时代，每个人需要负责的可能只是三个文件、一个功能模块、或者几个函数；但是 AI Coding 时代，功能粒度越来越大，每个人负责的功能越来越多。

如今更看重的是把事情做成，剩下的这件事情背后拆分出来的许多子任务都由 AI 来完成。这其中每件子任务做的是什么，以及怎么做，就是“靠谱”的含义，换而言之只需要**决策**即可。决策权在 AI Coding 的人手里。

## Vibe Coding 想解决的是什么问题

许多人都在 Vibe Coding，那 Vibe Coding 是为了什么？为了解决什么问题。

从不同的视角下看这个问题感受是不一样的。

- 地主老板的想法很简单：给我省钱！一个人干两个，乃至三个人的活，降本增效。
- 打工人只是想提升效率，更轻松，有更多的摸鱼时间罢了。

## Vibe Coding 现状

随着 AI Conding 的不断发展，有许多问题都一一暴露出来。工具使用，不同的业务场景，不同的人使用相同工具产出不一样等等等等。

### 过度使用 Skill

随着 AI 火了，Github 的开源局面逐渐 MD 化，自从 A/ 发布了 Sklls 协议。一个纯 MD 文稿的 Skill，Star 突然飙升到 100k+。这在之前是不太可能的事情。

越来越多的 Skill，解决各种各样的问题：

- PongTail 解决过度工程化的问题；
- SuperPowers：全流程的项目开发角色，完整的软件开发方法论；
- PUA：让 AI 不要提前放弃，尝试所有可能之后在给结论；
- ……

这些 skill 都解决了具体场景的问题，但是随着模型的能力越来越强。过度的 skill 只会干涉 AI。

很多人在使用 skill 的时候，不会打开每一个 MD 文稿，阅读到底写了什么？会给 AI 什么样的指令。不知道 skill 到底在干什么。

这就导致 — 虽然 AI 这样做了，到底是你的 Prompt 指引的还是 skill 指引的？为什么会有这样的结果。追究到底还是面向黑盒编程。不能全面掌控，不知道每一行代码会产生什么效果。最终只会越累越多**。**

### 百花齐放的 AI Coding 工具

越来越多的 AI Coding 工具，每家都对自家的模型做了优化，每家都有自己的设计理念，大厂也在二开。局面越来越负责。

- Claude Code：最早的 Coding CLI 工具，A/ 家的；目前仍然闭源，不过因为一次发板事故，源文件流了出来；
- Codex：Open AI 的 CLI 工具，Rust 编写，开源；
- Grok-build：Grok 的 CLI 工具，Rust 编写，因收集数据而被迫开源；
- Zcode：质谱的 CLI 工具，最近因收集用户选择和 Grok 一样，开源保命；
- ……

### 层次不齐的 AI 产物

在上一家公司的时候，公司自己维护的一款 CLI 工具，整合了 Claude，Codex 作为 CLI 的引擎。Bug 极多，而且维护不积极，丝毫不注重用户反馈（可能大厂都这样子，一个项目养活一个小团队的人 -;

那么：按道理说，每个人用的都是一样的 CLI 工具，提供一样的模型 List，产出应该是一样的。现状并不是。在我离职的时候，仍然有人安装了公司的 CLI 但是没有用起来的。

这其中有很多因素：

- 对 AI Coding 工具的理解；
- 接受并愿意尝试新事物的意愿；
- 对 Skill MCP 的应用；
- ……

尽管各类 AI 工具都对 Project 提供了专属于项目的 AGENTS.md CLAUDE.md 的配置等。除去人的影响因素之外。还有模型自身的影响，AI 每次 session 都是无记忆的，每次打开一个会话，对 AI 来说都是一个新的项目。对于之前的设计上下文只能来自于人的 Prompt。每次都会有差距，这种差距只会随着项目迭代的次数越来越多。

### 模型自身因素

从我自身使用来看，AI 存在这几个问题：

- 阳奉阴违：这点在早期的 Qwen 和 Gemini 模型上感受强烈，根本没做，写死的值说自己做完了；
- 过多输入：一次输入好几个问题时，AI 会选择性的完成，并不是完成所有的任务；
- 向前兼容：AI 总是会默认编写向前兼容的代码，即使对人来说，这是一个没有发布上线的新项目，新功能；
- 输出不透明：AI 在一些关键问题的处理上，总是会缺少一些关键信息的输出，（在他看来这信息并不重要；Github 有一个 skill 专门来解决这问题：https://github.com/ayghri/i-have-adhd
- 长任务：这应该属于工程性的问题，我放在这里是因为 cc 中，使用 Claude 和 Qwen 模型时，对会话压缩的效果大相径庭；
- ……

## 我在 Vibe Coding 中遇到的问题

在公司的一期项目中，我第一次尝试所有的功能都用 AI 来完成，用的是 GPT 6 Astra + High 模式来完成。skill 我安装了：

- PUA；
- Modern Go Guidelines；
- 马尾辫

结合之前的实践整理下遇到的一些问题：

### 业务场景下

这里的问题主要是结合对产品需求的理解上。我将产品产出的飞书文档和 html 原型一起给 Codex，让它基于此做一些需求的梳理和计划安排等等。遇到的一些问题如下：

1. html 原型文件阅读不全，理解不到位；
2. 后端接口梳理不完整，粒度不够或者太笼统等等，没有一个足够的度给 AI 去把握；
3. 对原型理解不到位；
4. **多次修改代码造成很多代码，字段冗余**；
5. 在 API 接口文档上，写一个 Apifox go skill，因为多次修改代码的原因，对接口字段叶有冗余；
6. 全程 AI 梭哈，在前端同学问我一些设计问题时，**只能让 AI 在解释，对代码不知根知底**，联调难度大，甚至成阻塞问题。

### AI Conding 工具

1. Codex 的上下文压缩在 AI 工具表现很好，可能和模型也有关系；

### 对代码直觉

其实上面的业务场景已经说到了，不能理解这个问题我觉得有必要拿出来单独说一下。在 AI 编写的设计文档一开始的时候，可能还会细看 review 一番。**但是到了中后期，写文档的事情都落到了项目仓库里的 docs 目录下。也没耐心去细看了。后期接口字段越来越多**。

这时候问题就暴露出来了，对于字段的取值，什么情况下拿什么值？对于业务的理解，这个 API 字段什么时候返回什么值等等。排查问题一筹莫展。不知从何入手。我感觉这本身就是工程师的大忌。自己掌控不了自己的东西，崩了的时候就很难解决了。

## 怎么解决 Vibe Conding 遇到的问题

对于上面几种问题，在第二阶段的时候。我做了一些调整。

1. 在使用 AI 的时候，**多提问**而不是返回给其注入上下文内容；这可以解决许多问题在我自身的实践体感上；
2. 对于业务理解，从数据库模型出发，将数据库和业务需求一起给 AI，从客户端到底层 DB 理解会更准确一些；
3. 对于接口字段冗余，一开始不要盲目下手，**先和前端，产品约定和明确字段需求**，避免之后大量修改，生产很多冗杂代码和字段；
4. 对于 AI 工具的冗余问题，仔细 review 选择性向后兼容，适度破坏兼容性，让 AI 产出最优解代码，有时候也是不错的选择；
5. 对于需求分析，我的做法比较激进，直接跳过此阶段，**以接口文档为准开展；有了 AI 之后效率提升很多；明确需要一个什么样的结果，比更早开始会少走许多弯路，磨刀不误砍柴工，知道做什么更重要；**
6. 保持勤奋：说了这么多自身之外的理由，我发现我的惰性比 AI 更大，还是要审核 AI 产出；
7. 贯彻到底 AI，吃饭前下班前，多让 AI Review 代码，说不定会有更好的效果。
